# Capstan CLI and API

Capstan follows the Fleet CLI parity proposal: every action in the editor has a named command, `<noun> <verb>`, and scripts or agents can run it without clicking. The commands are one registry of typed wrappers over the editor's pure edit operations (`src/engine/commands/`), so the editor and a command line cannot disagree about what an action does.

```bat
Capstan-CLI.bat commands
Capstan-CLI.bat <noun> <verb> [--option value ...] [--json] [--out <file>] [--yes] [--dry-run]
```

**`Capstan-CLI.bat` does not exist yet.** The line above is the planned launcher; read [Status](#status) before relying on any of this.

## Status

What exists today and is tested:

- The command registry: every command below, with typed, range-checked inputs.
- The JSON contract: `describeCommands()` returns `capstan.commands/1`, `runCommand()` returns the `capstan.result/1` envelope, and `exitCodeFor()` maps an envelope to the exit codes below. `bun scripts/commands.ts [--out FILE]` prints the commands document.
- The commands table in this file, which is generated from the registry. A unit test fails if it drifts or misses a command.

What is **not built yet** (issue #33):

- The `Capstan-CLI.bat` launcher. No command line runs a Capstan command today.
- The host bridge that carries a command from a launcher to the running page.

Until the bridge exists, the commands marked **Browser only** in the table (they need the live page: encoders, media bytes, file pickers, browser storage) answer `needs-browser` even when called from code, and the other commands can be run only by code that holds a project and calls `runCommand`. The flags and the token and safety rules below are the contract the launcher and the bridge are to follow; they are not features of the current host. Nothing here says otherwise.

`Capstan-CLI.bat commands --json` is to print the same list as JSON (schema `capstan.commands/1`, `"app": "capstan"`), with every option's type (`string`, `number`, `boolean`, `enum`, `id`, `json`), whether it is required, its allowed values or range, and the `needs` (`project` or `browser`), `destructive` and `atLeastOne` fields of the command. Until the launcher exists, `bun scripts/commands.ts` prints that document.

Option names are camelCase in the registry; a flag spells them in kebab case (`--ease-in` is `easeIn`). An `id` option takes the id of a clip, track, media item and so on; where the table says "one or more ids" it takes several, separated by commas.

## Flags and results

- `--json` prints one JSON document, the result envelope below.
- `--out FILE` writes that document to FILE as UTF-8 without a BOM. `bun scripts/commands.ts --out FILE` already does this for the commands document.
- `--yes` is required by the commands marked **Needs `--yes`**: the ones that discard or replace more than the thing they name (a track and its clips, all captions, the open project). In code it is `confirm: true`. Without it the command fails with `needs-confirm` and nothing changes.
- `--dry-run` checks the command and its options and reports what it would change, without running it for real. The envelope has `"dryRun": true` and a `changes` summary (item counts before and after, ids added, removed and modified, and project fields that changed) in place of the new project. A dry run does not need `--yes`, because it changes nothing. In code it is `dryRun: true`.
- Values typed on a command line are text, and the registry coerces them: `2.5` to a number, `true` or `false` to a boolean. Ranges and allowed values are enforced. A `json` option takes the JSON text.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | The command ran. |
| `1` | The command understood its options but could not do the work (`failed`: no such clip, a locked track, nothing to change), or it needs the running page (`needs-browser`). |
| `2` | A usage error (`usage`: unknown command, a missing, unknown or badly typed option) or a destructive command without `--yes` (`needs-confirm`). |

## Result and error envelopes

Every command answers with one object, and `runCommand` never throws. On success:

```json
{"schema":"capstan.result/1","command":"marker add","ok":true,"result":{"marker":"mrk_example"},"project":{"version":1}}
```

`result` is the plain data the command reports (ids made, text exported, counts); the table's description says what it holds. `project` is the project after the command and is left out of a dry run, which has `dryRun` and `changes` instead:

```json
{"schema":"capstan.result/1","command":"marker add","ok":true,"result":{"marker":"mrk_example"},"dryRun":true,"changes":{"counts":{"markers":{"before":0,"after":1}},"added":["mrk_example"],"removed":[],"modified":[],"fields":[]}}
```

On failure there is no `result` or `project`; there is an `errorType` and a message:

```json
{"schema":"capstan.result/1","command":"clip split","ok":false,"errorType":"failed","error":"No clip to split at that time (it must be inside a clip, not at its edge, on an unlocked track)"}
```

| `errorType` | Meaning | Exit code |
|---|---|---|
| `usage` | Unknown command, or a missing, unknown or badly typed option. | `2` |
| `failed` | The options were fine but the work could not be done. | `1` |
| `needs-confirm` | A destructive command without `--yes` (`confirm: true`). | `2` |
| `needs-browser` | The command needs the running page. | `1` |

In `--json` mode the failure envelope goes to standard output, as above. The project file itself is described in [PROJECT-FILE.md](PROJECT-FILE.md).

## Tokens

These are the rules the host bridge is to follow; the current host has only its per-launch session token, which lives in memory.

- A token never goes on a command line, where it would land in shell history, and never in a URL.
- Each Capstan session writes its token to a per-session token file under `%LOCALAPPDATA%\Capstan`, readable only by the current user (an ACL for that user alone),. The launcher reads that file; nothing prints it.

## Safety

- The bridge listens on loopback only, checks the `Host` and `Origin` headers, and sends no CORS headers, so a web page in another browser tab cannot call it. The API stays locked to the local user.
- Media is never uploaded and the commands make no network requests.
- Destructive commands need `--yes`, and `--dry-run` shows what a command would change first.
- Capstan is a single-user local tool, not a security boundary against other programs already running as you.

## Tests

- `tests/unit/commands.test.ts` and `tests/unit/commands-parity.test.ts` check the registry, the envelopes, the exit codes, and that each editor control in the inventory names a command that exists.
- `tests/unit/cli-doc.test.ts` runs `bun scripts/gen-cli-doc.ts --check` and fails if the table is out of date or leaves a registered command out.

To refresh the table after changing the registry: `bun scripts/gen-cli-doc.ts`.
